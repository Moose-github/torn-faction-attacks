# Ranked war research

The collector and saved findings live in **Admin → War research**. Collection is a finite, explicitly started job. The existing minute scheduler advances active jobs; paused, complete and frozen jobs make no Torn requests. Each tick has a single database lease and a bounded batch. No new Cloudflare service or recurring user automation is required.

Members can view **Miscellaneous → War research results** (`/war-research`). This display-only page automatically loads the most recently saved analysis of a matching frozen dataset. It shows sample coverage with expandable weekly, starting division and listed roster sections, saved cache prices, and every factor-versus-reward scatter plot with grouped medians, separately for combined-war and individual-faction rewards. It omits the most represented factions section. It has no collection, analysis, price, dataset or graph controls, no division-distribution or adjusted-association graphs, and no evidence cards. The authenticated `GET /api/war-research/results` endpoint returns only display data; it never fetches Torn reports or returns raw reports or collector controls. Results refresh once a minute while visible, with a 55-second server cache. New datasets without saved analysis do not replace the displayed results. Older analyses missing coverage or graphs show explanatory empty states. Deploy the Worker and dashboard together; no migration is required for this page.

The results page also shows the **top 5 wars by gross reward value** above the graphs, ranked by both factions’ combined rewards using the saved analysis prices. The ranking queries every eligible report linked to that frozen dataset and within the saved analysis date range, not the graph’s sampled points. If either faction has any positive reward quantity without a price, the entire war is excluded; zero prices and empty rewards remain valid. Ties use ascending war ID. Only the five selected reports are loaded from D1, and only aggregate faction stats reach members. Each row expands to show both factions’ starting divisions, reward values, attacks, scores, roster counts, participation and attack concentration, plus combined score, attack balance and a Torn report link. Member-total discrepancies are flagged without excluding a fully priced war from the reward ranking. This works with existing saved analyses without reanalysis, migrations or Torn calls.

## Use

1. Opt a submitted pool key into **Enemy scouting** in Settings. War research uses that same permission; there is no separate research key option. Keys with only the retired War research permission are not used unless Enemy scouting is enabled. Research does not use fallback keys or keys without a known owner, and collection starts only when an administrator starts a dataset.
2. Create a named dataset with completed UTC days and a total request budget. The default 5,000 calls cover roughly four hours at one owner's theoretical maximum pace; other feature use and retries can make collection slower, while multiple owners can make it faster. Start collection to fetch reports from Torn. Raw report uploads are not supported. Requests include listing pages, reports and failures. All starting ranks must be inspected because the listing has no rank fields. Both starting ranks must be Platinum for inclusion; forfeits are excluded.
3. Pause whenever needed. Resume keeps the cursor and reuses already saved reports. An explicit larger total budget is required after exhaustion. Temporary failures retry automatically; exhausted retries and issues requiring review pause without discarding progress.
4. Freeze the reports already saved. Pending reports are removed from that sample. The snapshot cannot resume or change; create a new dataset for a new era or larger sample. Shared raw reports are immutable and deduplicated by war ID.
5. Enter full-dollar cache prices in the frozen dataset and click **Analyse collection**. Blank prices mean unknown; zero means a known $0 value. Reports are read in batches from saved storage, analysed in a background browser worker, and compact findings are saved automatically. No download or upload is required, including for large raw exports. Keep the tab open until it finishes. Cancel stops calculations without changing the collection; previous findings remain available. A save already accepted by the server cannot be undone by cancellation.
6. View coverage, factor comparisons, evidence cards and graphs for combined and individual faction rewards. Change prices and choose **Reanalyse collection** when needed. Analysis makes no Torn requests. Previous analysis versions remain stored.

**Optional offline workflow:** Under **Optional backup and offline analysis**, download the raw dataset. Run `research/Analyze.cmd` on Windows (or `python research/analyse_dataset.py export.json --prices prices.json`), with NumPy and Matplotlib installed using `pip install -r research/requirements.txt`. Upload the generated `upload-analysis.json` to the same dataset. The raw export may be tens of megabytes; only the compact findings belong in the upload field, whose limit remains 1.5 MB.

The analysis preserves the local prototype's screening gates (100 valued wars, 20 factions, model sample size/rank checks), outcome/division/roster/month controls, two-way war/faction clustered uncertainty, chronological-half checks, faction-exclusion sensitivity, and collinearity checks. It withholds adjusted estimates for the August 2026 transition or mixed eras. It reports associations, not causal effects, payout forecasts, caps or a cross-rank scaling rule. Member counts remain proxies requiring validation against known wars. A truncated chronological sample is not a random sample.

### Whole-war rewards

New analyses include two views, with **Combined war pot** selected by default. Whole-war value is the sum of both factions' gross cache values at the same prices, counted once per war. Missing prices on either side exclude the entire pot from monetary analysis; audit problems on either side exclude it from the adjusted model. The faction view remains available separately. Existing uploaded faction-only analyses still display; rerun the frozen export to add whole-war results without new Torn requests.

The whole-war model separately examines combined attacks, combined score, pooled participation, pooled within-faction top-20% attack concentration, duration, attack balance and score balance. Balance is the smaller side's share of the total (0 to 0.5). Controls are combined roster size, roster balance, winner and loser starting divisions, and month. Each war supplies one observation. Its uncertainty estimator allows wars sharing either faction to be dependent, even when factions switch winning/losing roles or meet repeatedly; it uses the [dyadic sandwich method](https://arxiv.org/abs/1312.3398) with an n/(n-p) degrees-of-freedom correction. Wider network dependence can still remain.

The display shows the combined gross value before any agreement between factions. No split calculator or expense deductions are included. The API does not disclose which wars were termed, actual agreed splits or transfers.

### Coverage and factor evidence

New analyses show saved and eligible wars by UTC week (including empty weeks), winner/loser starting divisions, listed faction roster sizes, and the ten most represented eligible factions. Both sides count once in whole-war coverage. Counts describe the saved sample, not the total population. New freezes preserve discovered/saved/pending counts and whether discovery finished before pending links are removed. Older frozen datasets and exports show collection completeness as unknown; their missing history cannot be reconstructed by rerunning analysis.

Both reward views include explicit questions about attacks, score, participation, attack concentration, duration, roster size, and divisions. Whole-war results also compare attack and score balance; faction results include opponent score and winning versus losing. Observed groups use quartile boundaries without splitting ties, or categories for division/outcome. Each group shows observations, distinct wars/factions, mean and median gross value. Comparisons use the same fully priced observations with consistent member totals as the model. A descriptive group contrast is not an adjusted effect.

Evidence cards separate **observed trends** from **adjusted associations**. A positive or negative observed label requires at least three factor groups with at least 20 distinct wars in every group, and both group means and medians moving consistently in that direction with different first and last values. This is a descriptive screening rule, not a significance test; ties, small samples and irregular shapes receive explicit alternative labels. It can show a clear observed trend even when an adjusted estimate is unavailable or points in another direction.

Adjusted differences compare the 25th and 75th percentiles and show approximate 95% intervals, percentages relative to the sample mean, chronological-half consistency, the most-represented-faction sensitivity check, and factor overlap (VIF). An interval excluding zero with both direction checks passing is a promising association when VIF is below 10. With VIF at least 10 it is instead labelled **Positive/Negative association; overlapping factors**: the estimated direction remains supported by these checks, while the separate contribution is harder to isolate. Overlap alone no longer produces a generic Uncertain label. Missing checks or intervals including zero remain uncertain; direction reversals remain mixed evidence. These are exploratory, model-dependent classifications, not causal conclusions.

Observed percentage differences use the first group's mean. Zero baselines have no percentage. Division/outcome comparisons remain descriptive. An unavailable sensitivity check is explicitly unknown and cannot qualify a result as promising. Intervals are not adjusted for multiple comparisons; the cards do not provide predictions or targets. Existing saved analyses remain readable; choose Reanalyse collection to generate the new assessments using the same saved reports and prices.

Reanalyse an existing frozen collection to add these sections. Both the optional standalone HTML and dashboard show the evidence. Older analyses remain readable. No additional Torn calls are made by analysis or viewing.

### Reward graphs

Both reward views show factor-versus-reward scatter plots, reward distributions by starting Platinum division pairing, and adjusted associations with approximate 95% uncertainty intervals. Select a factor and optionally show grouped medians. Distribution boxes show the middle 50%, median and full minimum-to-maximum range; they are not confidence intervals. Individual faction distributions separate wins and losses. Combined-pot pairings are winner / loser; faction pairings are own / opponent. Weekly coverage remains a collapsed detail in the dashboard, not a graph.

Observed plots use the fully priced, consistent-member-total sample used for factor evidence. Scatter plots retain at most 1,000 dots per reward view, selected by a stable hash of war/faction IDs. This repeatable sample may omit extremes; axes, grouped medians and distributions always use all usable observations. The upload remains compact even for large datasets. Adjusted charts reuse the evidence cards' estimates and intervals; different factor ranges do not represent equally achievable interventions.

Selecting war score also shows fixed score-range comparisons using the complete usable sample: 0–5k, 5–10k, 10–15k, 15–20k, 20–25k, 25–30k, 30–40k, 40–50k and 50k+. Lower bounds are inclusive; finite upper bounds are exclusive. Each range shows observation and distinct-war counts, mean, median and the middle 50% of rewards; empty ranges remain visible and ranges with fewer than 20 wars are marked sparse. The middle 50% is reward spread, not a confidence interval. These ranges are fixed across datasets, rather than fitted to support a suggested cutoff. They help inspect local patterns but do not estimate a plateau or an optimal score.

The standalone HTML embeds SVG figures with no external assets. Matplotlib is needed for those offline figures; if it is missing, the report explains how to install it, while dashboard chart data is still generated. Reanalyse a frozen collection to populate the plots without additional Torn requests. Older analyses remain readable.

Test the offline aggregation, coverage, evidence and graphs with `python -m unittest discover -s research -p "test_*.py"`.

## Capacity

Research reserves its allowance transactionally **before** calling Torn and counts failures. It uses at most 20 attempts per rolling 60 seconds per known owner across all their keys, stops when observed dashboard use plus unresolved research reservations reaches 50 requests in the past 60 seconds, and leaves five calls below the selected key's configured minute allowance. Unresolved reservations may briefly overlap their usage log entries; this conservatively leaves extra headroom. Only one research batch runs at once. Each batch can start up to 120 requests within a 45-second work window, fetching up to four distinct reports concurrently; discovery pages remain sequential. Keys are loaded/decrypted once per batch and rotated between requests. Every reservation still rechecks current permission, key status, cooldowns and limits in the database. Report and progress writes are committed together. Already reserved requests receive their full 15-second timeout and finish before the lease is released; pausing prevents new reservations and freezing waits for in-flight work. Database overhead and latency can reduce actual throughput. Eligible runs rotate by their last collector check. These controls constrain this collector; existing features and external apps do not all share an atomic owner-wide limiter. Torn's account-wide limit is shared across keys and apps; the collector cannot guarantee capacity used elsewhere.

### Recovery and live collection health

Timeouts, HTTP 408/5xx errors and recognised temporary Torn errors retain the cursor and schedule retries with increasing delays of 60, 120, 240, 480 and at most 900 seconds. Five accumulated service failures without a successful wave pause the run for manual review. Successful report saves or valid listing pages reset the prior counter. If a concurrent wave also contains service failures, its successes are saved first, then its failures are counted and backoff is applied; no further wave starts in that tick. Key failures are handled separately: invalid, paused or insufficient-permission keys receive a 24-hour research-only cooldown, and other available keys continue. These research cooldowns do not disable other dashboard features. Rate limits cool every key belonging to the affected owner for two minutes (24 hours for Torn's daily limit); these owner-wide cooldowns also protect other features and are visible in Settings. Upstream error text is never copied into research status messages.

Unfinished, missing or malformed individual reports are deferred independently, with increasing retry delays and a maximum of five failed attempts. Fresh reports and further discovery can continue while they wait. When discovery is finished, the run waits for due retries; it pauses if only exhausted reports remain. Explicit Start / resume renews exhausted retry allowances and clears research-only key cooldowns, allowing corrected keys to be tested again within the total budget. It does not clear owner-wide rate cooldowns or shorten a report's pending delay. Manual pause and freeze remain authoritative. Unexpected listing shapes, API errors without an established recovery rule, and unsafe pagination pause the run instead of skipping data.

Collection health shows last response/save/check timestamps, report reuse, eligible reports, pending retries, exhausted reports, calls in the last minute, five-minute pace/failures, owner/key availability and remaining budget. The time estimate concerns budget exhaustion at the recent pace, not dataset completion. Earlier runs have unknown timestamps/reuse history rather than reconstructed estimates. Unresolved report details can be downloaded in full without Torn calls. Freeze preserves their reasons and retry counts even if another dataset later saves those wars; coverage also records deferred/exhausted counts and warns about the resulting omissions.

Pagination accepts both `ASC` and `asc` in Torn's next-page links and stores a canonical `ASC` cursor. It rejects descending or missing sort orders, external URLs and out-of-range dates, and strips credentials before storing links. A self-link is treated as the end only when the requested page limit is 100, fewer than 100 valid, distinct wars are returned, every returned war starts exactly at the current lower boundary (or the page is empty), there is no offset and the requested upper bound still covers the dataset's end. Boundary wars are saved and deduplicated before discovery finishes. Full repeated pages, links to earlier pages and ambiguous loops still pause without advancing timestamps or skipping tied wars; the message includes the page's war count. Runs paused by these pagination compatibility checks can use Start / resume after deploying the fix; their cursor and request budget are retained.

The API's unsuffixed `Platinum` rank is accepted as the base division, represented internally as 0 and displayed as `Platinum` (or `P base` in compact graphs). It remains distinct from `Platinum I`; raw report labels are preserved. Existing numbered division values and older uploaded analyses retain their meaning. Previously deferred base-rank reports can succeed on their next retry after deployment; exhausted retries require Start / resume. Frozen samples are not changed.

## Deployment and validation

The revised observed/adjusted evidence and score bands require both the dashboard and Worker deployments because the saved-analysis validator accepts the new fields and status labels. They need no schema migration. Previous saved results remain readable.

Direct analysis reuses the existing Worker endpoints and needs no new database migration. The browser worker runs the same incremental Python engine as the offline CLI, using pinned Pyodide 0.27.7 and NumPy. `npm run dev` and `npm run build` in `dashboard` prepare runtime assets under the ignored `public/research-runtime/` directory. The initial build downloads the pinned NumPy wheel from jsDelivr and verifies its SHA-256 against Pyodide's package lock. Cached valid wheels are reused. Deploy the entire dashboard build, including runtime assets. Browser runtime downloads come from the dashboard origin; report contents are never sent to a runtime CDN. The runtime loads only when analysis starts. First use requires a larger download, and analysis stops if the tab closes or leaves this workspace.

Apply migrations through `0178_ranked_research_recovery.sql` to the Worker D1 database, deploy the Worker and build/deploy the dashboard together. Migration 0178 adds recovery counters, health timestamps, an attempt index, research key cooldowns and a per-run report retry table. It does not rewrite existing reports or frozen snapshots. Collection remains inactive until an administrator opts in a key and starts a run. Unfinished reports are never cached as final results.

Run `npm test -- tests/rankedResearch.test.ts src/http/adminRoutes.test.ts src/tornKeyPool.test.ts`, worker TypeScript checking, `npm --prefix dashboard run build`, and `npm run schema:check`. The tests cover budget exhaustion, failed attempts, shared owners, cursor safety, resumability, immutable snapshots, filtering and admin route protection. Use a separate fixture dataset for UI verification; do not trigger live collection during checks.
